## 2. Ground truth — re-probed, not trusted

Per the spec's own instruction (§3: "Re-probe all of it... treat §5 as
claims to re-probe, not facts"), everything in the ground-truth table was
checked against the live repo before implementing, and two things in the
spec itself turned out not to hold:

1. **Hazard B's claim that `skill-candidate` "has the same shape" as
   `diagnosis` is false against the live payload.** Both call sites that
   emit `type="skill-candidate"` (`run_pass_error_cluster` and the
   insights pass's `_build_insight_proposal`) use
   `args = {task, occupation, procedure, verification, preconditions,
   failure_modes, provenance, source_tier, quality}` — never
   `error_text`/`context`. Narrowing skill-candidate identity to
   `{type, call, args.error_text, args.context}` as instructed would have
   made `args.get("error_text")` and `args.get("context")` resolve to
   `None` for every skill-candidate proposal ever produced, collapsing
   all of them onto one fingerprint regardless of task — worse than the
   defect this fix closes, and the exact failure mode Hazard A warns
   about. **Deviation:** `_NARROW_IDENTITY_TYPES = {"diagnosis"}` only.
   skill-candidate stays on full-body identity until it actually carries
   a stable error_text/context pair. Documented at length in the code
   comment above `_NARROW_IDENTITY_TYPES`.

2. **The fix doesn't retroactively help historical rows** — found live,
   not predicted. See §4.

Everything else in the ground-truth table (line numbers, `sub_passes`
binding site, fingerprint/ignored-keys locations, `repeat_prior`'s
existing `APPLIED` coverage, the 14/3/14 diagnosis counts, the 67-doc/
0-repeat `lse-errors-1024` count, the 843-passed baseline) checked out
exactly as stated.

## 3. Hazard C — decided, not inherited by accident

`repeat_prior()` already matches `REJECTED` priors, unconditionally, for
every proposal type — this was true before this change and is unrelated
to the narrowing. **Decision: leave it.** Once a diagnosis is narrowed to
`error_text`+`context` identity, an operator-rejected diagnosis will not
be re-offered even if a later run drafts a materially better one. This is
deliberate: consistent with how every other proposal type is already
treated (a `REJECTED` `kb-fact` or `dedup` pair is equally never
re-offered today), avoids a type-specific carve-out that Hazard B's
"scope narrowly" spirit argues against, and doesn't require inventing new
state. The cost is real — a rejected-for-being-wrong diagnosis could later
turn out right and won't resurface — but it's the same cost the rest of
the system already accepts, not a new one introduced here.

## 4. What V3 found live, and the migration it required

Ran a real single-pass `error-cluster` cycle against production
(`--run-source manual --skip-session-guard --no-dry-run`; dreamer already
reachable at `127.0.0.1:8080`, no node wake needed): `run_9244fa42`,
attempt `att_01cc013f`, **SUCCEEDED**, 5 new `diagnosis` proposals.

One of them, `prp_597940d2` (`error_text="ERROR: Command timed out after
200 seconds."`, `context="tool=execute_command exit_class=timeout"`), is
byte-identical to a doc already `APPLIED` into `lse-errors-1024`
(confirmed via ES `match_phrase` search, 1 hit, `occurrence_count: 2`).
Per the fix it should have superseded. **It came back `PENDING`.**

Root cause: `repeat_prior()` matches on the **stored** `fingerprint`
column via `WHERE fingerprint=?`. Every existing row in the live
`proposals` table — including the row that fed that `APPLIED`
`lse-errors-1024` doc — was fingerprinted under the pre-fix, full-body
formula, before this code existed. The fresh proposal's fingerprint is
computed under the new narrow formula. Same semantic identity, different
hash, no SQL match. **The code fix is correct and works prospectively
(new-vs-new, proven by test 5) but cannot retroactively catch
new-vs-pre-fix-historical repeats** — which, on day one of deployment, is
every repeat that matters, including the 5 duplicates named in the
spec's own §11 context.

This gap isn't in the spec (§5/§7/anti-goals never mention a backfill).
Flagged to the operator rather than silently patched around; operator
chose "write a backfill migration."

**`scripts/backfill_diagnosis_fingerprints.py`** — dry-run by default,
scoped to `proposal_type='diagnosis'` only (same Hazard B scoping as the
code fix):

- Phase 1: recompute `fingerprint` for every diagnosis row from its
  stored `payload_json`, using the live `traum_state.proposal_fingerprint`
  (imported, not reimplemented). No state changes — `APPLIED`/`REJECTED`/
  etc. rows keep their state, they just become correctly matchable as
  `prior` candidates.
- Phase 2: walk all diagnosis rows by `created_at ASC`; for each new
  fingerprint, the first repeat-eligible row (same eligibility set as
  `repeat_prior()`, including the `SYSTEM_REJECTED` malformed/noop/
  invariant carve-out) becomes the anchor. Any later row **currently**
  `STAGED` or `PENDING` gets superseded, reason
  `exact_already_resolved_or_queued:{prior_id}:{prior_state}` — the exact
  format `record_proposals` itself now writes (§5.3 fix). Idempotent:
  re-running after apply reports 0 changes.

Verified end-to-end on a copy of the production db before touching the
real one (dry-run → apply → confirm state → re-run dry-run → 0 changes).
